# 1. Abstract

> **狀態：** Proposal 草稿；下列系統與評估方法皆為規劃，非已完成的實驗結果。

**A. Attention Getter — Motivation：** 臺中市民倒垃圾需配合垃圾車沿街或定時定點收運時間，錯過時可能需等待下一次收運，或尋找其他收運點。臺中市政府環境保護局指出，「台中垃圾清運大車隊」系統已服務市民超過十年；截至 2026 年 9 月，涵蓋全市 29 個行政區、370 多條清運路線與 2 萬多個清運點，App 累積下載量接近 65 萬次 [I1]，顯示市民對清運資訊具有持續需求。

**B. But — Challenge：** 現有服務提供車輛位置、清運進度及預計抵達時間，但使用者仍須自行比較附近收運點與步行時間，判斷現在前往哪個點較有機會趕上垃圾車 [I1][I11]。實際抵達時間可能受交通與勤務等因素影響，表定時間不等於實際到點時間。此外，政府資料開放平臺標示車輛動態資料每 10 分鐘更新 [I9]，定位時間與查詢時間可能存在落差，影響即時決策。

**C. Cure — Proposed Solution：** 本專題提出 GarbageGo，一個以臺中市垃圾清運為情境的 Domain AI Agent（領域智慧代理人）。系統預計綜合使用者位置、步行範圍、候選收運點、垃圾車 ETA、資料新鮮度與風險，推薦預估較可能趕上的收運點；主要方案風險過高時，搜尋其他可行方案，並於資料不足或沒有可行方案時說明限制。

**D. Development — Method：** 系統規劃整合 GIS Engine、ETA Engine、Recommendation Engine 與 LLM Agent。GIS Engine 依步行路網估計至候選點的步行時間；ETA Engine 結合可取得的車輛動態、路線、收運點及歷史資料，估計垃圾車到點的剩餘時間；Recommendation Engine 評估時間可行性並排序；LLM Agent 則理解自然語言需求、協調工具及說明結果。核心決策沿用下列概念公式：

```text
slack(s) = truck_ETA(s) - walking_time(s) - safety_buffer(s)
```

其中，`truck_ETA(s)` 是從查詢時間起至垃圾車預估抵達收運點 `s` 的剩餘時間，`walking_time(s)` 為預估步行時間，`safety_buffer(s)` 為安全緩衝；各項均以相同時間單位表示。緩衝可考慮 ETA 誤差、資料年齡等風險，具體方法待資料與實驗驗證。`slack` 為正僅代表在目前假設下初步可行，不保證趕上。

**E. Experiments — Evaluation：** 本專題預計使用臺中市車輛動態、定時定點收運與步行路網資料，並評估可取得的歷史軌跡。比較方法規劃包含最近點選擇、固定步行速度與直線距離估計、表定時間及歷史平均到點時間；前兩者分別為選點策略與步行時間估計方法，將在明確設定下與時間可行性推薦比較。候選指標包括 ETA 的 MAE、RMSE、步行時間誤差、趕上率、誤判率、錯過率、備案成功率，以及資料年齡對推薦品質的影響。公開 API 回應不直接提供歷史軌跡；本組已有自行蒐集的資料，但其適用性、可信的實際到點與步行時間資料，以及各推薦指標的計算方式仍須驗證與定義。

**F. Findings — Expected Outcomes：** 本專題預期建立結合步行時間、垃圾車 ETA 與風險的時間可行性推薦方法，提供推薦依據、資料時間與備案，並透過實驗比較不同策略的表現。系統是否能提高趕上率或降低使用者時間成本，須待適當資料及評估完成後確認；目前不預先宣稱效能數值。
