## 2. 垃圾清運作業與「定時定點」制度

臺灣採「垃圾不落地」的收運方式，民眾必須在表定時段內把垃圾直接交給垃圾車（[B1] 對此制度有說明，見 `03a-related-work-ai.md`）。臺中的收運點資料也呈現這種作業型態：20,090 個收運點都有固定的收運時段，其中 95.1% 為沿街清運、4.8% 為定點清運（見 `docs/research/opendata-api-check.md` §9）。臺中市環保局公告的 115 年國定假日收運表 [C7] 也呈現兩種方式的差別：平日沿街收運，11 個國定假日則停止沿街收運、改為定時定點，每個定點公告 10–30 分鐘的停留時段，以北區為例共 20 個定點。

近期研究開始把即時資料帶進收運規劃。Hassan 等人 [C1] 在杜拜以 GIS 建置智慧廢棄物管理系統，用現場 GPS 定位的垃圾桶資料最佳化收運路線，3 條路線的行駛距離都縮短，CO₂ 排放平均減少 19.1%；不過比較基準是另一個路徑模型，而不是實際營運路線。Maciel 等人 [C2] 統合 11 篇研究，發現 IoT 路徑最佳化平均可減少 21.51% 收運距離；但模擬研究減少 39.79%，使用實際營運資料的研究只減少 12.37%，顯示模擬結果容易高估實際效果。

這兩篇研究的服務對象都是收運單位，目標是縮短路線與降低成本，沒有討論居民端：民眾如何得知垃圾車何時到、能不能趕上。

## 3. 影響垃圾車到點時間的因素

垃圾車何時到某個收運點，取決於前面每一站停多久、站與站之間開多久，以及當天的垃圾量與交通狀況。

Hamontree 等人 [C3] 在曼谷 Lat Krabang 區以兩週現場調查建立收運點與垃圾量資料，並用關聯規則與 K-means 分析垃圾量模式。結果顯示，垃圾量會隨星期與區域類型變化：商業區在週末較多、住宅區在週一較多，其中中量住宅區那一群收運點的週一垃圾量比平均高 31.5%，作者推測是累積了週末的垃圾。AI 技術文獻中的 [B1] 也有相同方向的發現：新竹停收日後的週一、週四，垃圾車行駛時間較長（見 `03a-related-work-ai.md`）。

不過 [C3] 的交通採靜態假設，也沒有量測收運點停留時間。本組 API 實測則看到臺中的相關現象：收運點資料中週三、週日幾乎沒有一般垃圾時段；抽樣的 GPS 點中約 18% 位於處理廠或焚化爐，代表中途卸載會影響後續到點時間（見 `docs/research/opendata-api-check.md`）。國定假日改為定時定點後，收運方式與停留時間都和平日不同 [C7]。臺中市環保局內部其實已統計各車的停駐時間與準點率 [C4]，但這些數據沒有公開。這些因素實際造成多少延誤，仍需要用可取得的臺中本地資料估計。

## 4. 既有垃圾車查詢 App 與服務

臺中市環保局於 2014 年建置「臺中垃圾清運大車隊」網站與 App，App 於 2014 年底上線 [C4]。系統整合 29 個行政區、500 台以上垃圾車與 300 多條路線，車輛 GPS 每 20 秒回傳一次位置。提供的功能包含即時位置、附近清運點查詢、收藏清運點，以及垃圾車即將到點時推播通知。系統會統計每部垃圾車的每日平均抵達時間、停駐時間與準點率，以大數據分析輔助調整班表；文件提到可以預測垃圾車抵達時間，但未說明方法與準確度。

與本專題最接近的是 Duran Guerrero 等人 [C5] 的研究。他們在祕魯利馬一個社區建置 IoT 系統：司機手機每 30 秒回傳一次 GPS，垃圾車接近某個區域時，系統就推播通知到居民手機，並讓家中的喇叭響起。以 70 位居民進行前後測，垃圾停留在公共空間的時間由 12.5 分鐘降至 1.2 分鐘，知道收運時間的居民由 30% 增至 95%。這證明讓居民掌握垃圾車動態確實能改善丟垃圾的時機。不過研究只涵蓋單一社區，沒有對照組，停留時間也由居民自行填報；通知只在垃圾車接近時觸發，全文沒有處理到點時間預測或居民的步行時間。

現有服務已能告訴民眾「垃圾車在哪裡」，但查詢結果仍需要民眾自己判斷：從自己的位置走到清運點，能不能在垃圾車離開前趕到。

## 5. 政府 OpenData 的品質與限制

Tejedo-Romero 等人 [C6] 調查巴西政府開放資料平臺 190 個機關的資料管理人員，共回收 215 份問卷。71% 的受訪者表示平臺上有標示更新頻率，但只有 54% 表示資料確實依標示的頻率更新；61% 有發布詮釋資料，但詮釋資料與資料同步更新的只有 48%；資料粒度夠細的只有 37%，69% 表示資料發布仍未自動化。迴歸分析顯示，資料傳播管道與支援資源（如預算、人力）是影響資料品質最主要的因素。作者也指出，這些結果來自管理人員的自評，不是直接檢查資料。

本組的 API 實測（見 `docs/research/opendata-api-check.md`）也觀察到類似問題：公開 API 約每 5 分鐘才更新一次，比 [C4] 內部系統的 20 秒粗得多；約 18% 車輛的位置超過 30 分鐘未更新；`location` 欄位是文字描述，無法直接對應清運點；API 也不提供歷史資料。平臺上的詮釋資料同樣不完整：更新頻率標示為「每日」，與實測不符，欄位也沒有定義說明，與 [C6] 發現的「標示的更新頻率與實際不符」屬於同一類問題。

## 6. 小結：現有研究的共同限制

1. **以營運端為主**：收運研究多關注路線長度與成本 [C1][C2]，較少處理居民端「能不能趕上垃圾車」的問題。
2. **查詢服務停在「顯示位置」**：既有 App 與近期研究提供即時位置與接近通知 [C4][C5]，但到點時間的預測方法與準確度未公開，也不考慮民眾走到清運點所需的時間。
3. **到點時間的影響因素缺少本地量測**：垃圾量隨星期與區域變化 [C3]，但該研究只分析垃圾量與距離，交通採靜態假設，也沒有量測停留時間；臺中環保局內部的停駐時間統計也未公開 [C4]，這些因素在臺中造成多少延誤，仍需本地資料估計。
4. **公開資料的品質與時效有限**：開放資料的更新與詮釋資料仍有不足 [C6]；公開 API 的更新頻率也遠低於機關內部系統 [C4]，且不提供歷史資料。

以上限制將在 `03c-research-gap.md` 中與 AI 技術文獻（`03a`）一起整理成 Research Gap。
