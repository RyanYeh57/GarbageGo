## 3. 實測方式

- 在本機以 cron 每 10 分鐘呼叫一次 API（每小時的 :02、:12、:22…）。本文件的統計都依這個排程收集。
- 確認 API 約每 5 分鐘更新後（見第 6 節），2026-11-06 23:32 起改為每 5 分鐘呼叫一次（:02、:07、:12…），在 API 每次更新後約 2 分鐘抓取。
- 每份回應整份保存為一份「快照」；內容與上一份完全相同時略過不存。
- 拆出每台車的 GPS 點，以 `car + time` 去重後存入 SQLite。

## 4. 欄位說明

所有欄位都以**字串**回傳，數值欄位使用前需要轉型。平臺頁面只列出欄位名稱，沒有欄位定義，以下說明來自實測觀察。

| 欄位 | 說明 | 範例 |
|---|---|---|
| `lineid` | 代碼，實測每台車固定對應一個值；意義待確認 | `24908` |
| `car` | 車牌 | `KED-1385` |
| `time` | GPS 回報時間，台北時間，格式 `YYYYMMDDTHHMMSS` | `20261103T193953` |
| `location` | 文字地點描述，**不是清運點編號** | `臺中市龍井區 龍昌路` |
| `X` | 經度 | `120.504613` |
| `Y` | 緯度 | `24.210510` |
| `SpeedValue` | 車速，單位待確認（數值範圍推測為 km/h） | `37` |
| `OverSpeed` | 是否超速，`Y` / `N` | `N` |

範例（一筆）：

```json
{"lineid": "24908", "car": "KED-1385", "time": "20261103T193953", "location": "臺中市龍井區 龍昌路", "X": "120.504613", "Y": "24.210510", "SpeedValue": "37", "OverSpeed": "N"}
```

- `time`：980,775 筆全部符合 `YYYYMMDDTHHMMSS` 格式，沒有格式錯誤。
- `location` 的內容類型（隨機抽 2,000 筆，以關鍵字粗略分類）：

| 類型 | 比例 | 例子 |
|---|---|---|
| 地址／路口 | 38.5% | `山腳里 中山一路與龍山街1號(巷口)` |
| 清潔隊／區隊 | 27.4% | `后里區隊汙水處理位置` |
| 處理廠／焚化爐 | 18.4% | `清淨園區` |
| 其他 | 12.5% | `南屯02`、`石岡回收場` |
| 里名 | 3.4% | — |

## 5. 座標系統

**WGS84 經緯度（EPSG:4326）**，`X` 為經度、`Y` 為緯度，小數 6 位。可以直接寫入 PostGIS 的 `geometry(Point, 4326)`，不需要轉換座標。

- 實測範圍：經度 120.17–121.83、緯度 22.93–25.08。
- 以經度 120.4–121.5、緯度 23.9–24.5 粗估臺中範圍，有 2,363 筆（0.24%）落在範圍外，可能是跨縣市行駛或定位異常。
- 沒有空值或 (0, 0) 座標。

## 6. 更新頻率

- **API 約每 5 分鐘產生一次快照**，時間落在 :00、:05、:10…。這是實測推定，不是官方公告。
- 判斷方法：
    1. 本組 cron 都在 :x2 分抓取。抽查 1,518 份快照，每份最新一筆 GPS 都比抓取時間早約 2 分鐘（中位數 123 秒，九成在 118–131 秒之間），而且都落在整 10 分前後。垃圾車內部每 20 秒回傳一次 GPS（見 `03b` [C4]），如果 API 是即時資料，最新一筆應該只差幾秒；因此 API 是定時產生快照，:x0 到 :x2 之間沒有更新。
    2. 2026-11-06 23:29:22 另外手動抓取一次，最新一筆 GPS 為 23:24:56，代表 23:25 也產生了快照，之後到 23:29 沒有再更新。
- 本實測期間的收集排程為每 10 分鐘一次，只抓到約一半的快照；2026-11-06 起已改為每 5 分鐘（見第 3 節）。
- 平臺頁面標示的更新頻率是「每日」，與實測不符，以實測為準。
- 每次抓取只有部分車輛有新位置。每次抓取（間隔 10 分鐘）新增的 GPS 點中位數為 175 筆，隨時段變化：

| 時段 | 每次抓取新增 GPS 點（中位數） |
|---|---|
| 07:00–20:59（清運時段） | 約 250–390 筆 |
| 06:00–06:59、21:00–21:59 | 約 220–260 筆 |
| 22:00–05:59（深夜） | 約 150–170 筆 |

## 7. 缺漏與限制

| 問題 | 實測結果 |
|---|---|
| 沒有歷史資料 | API 只提供每台車最新位置，錯過的時段無法補回 |
| 停止回報的車輛 | 2026-11-03 19:42 的快照中，663 台有 118 台最後回報超過 30 分鐘，8 台超過 1 天，最舊停在 2025-09-29 |
| 回傳空資料 | 1 次回傳空陣列（2026-10-22 16:22） |
| 座標超出臺中範圍 | 2,363 筆（0.24%），見第 5 節 |
| 異常車速 | 4 筆超過 120，最大 190 |
| 超速旗標 | `OverSpeed = Y` 共 1,504 筆（0.15%） |
| 停車點占多數 | 81% 的 GPS 點車速為 0 |
| `location` 不是清運點 | 無法直接從欄位判斷車輛是否已到某個清運點 |
| `lineid` 對應不唯一 | 每台車只對應一個 `lineid`，但有 4 個 `lineid` 對到多台車 |
| 平臺詮釋資料不準確 | 更新頻率標示「每日」，實測約每 5 分鐘；欄位沒有定義說明 |

收集端的缺漏（非 API 問題）：共 24 次間隔超過 15 分鐘。最長一次 6 小時 40 分（2026-10-15 本機重開機），其餘都在 40 分鐘內，原因為 API 內容未更新或本機網路暫時失敗。

### 9.2 欄位

| 欄位 | 說明 | 範例 |
|---|---|---|
| `area` | 行政區 | `中區` |
| `village` | 里別 | `中華里` |
| `car_licence` | 負責車輛車牌 | `312-UX` |
| `caption` | 清運地址（不含行政區） | `中華路一段143號` |
| `task_type` | 清運方式 | `沿街` |
| `g_d1_time_s`～`g_d7_time_e` | 一般垃圾各天的開始／結束時間，格式 `HH:MM`，空字串表示當天不收 | `15:25` |
| `r_d1_time_s`～`r_d7_time_e` | 資源回收各天的開始／結束時間，格式同上 | `15:25` |

**沒有經緯度欄位。** 收運點只有文字地址，GIS Engine 查附近收運點前，需要先把 `area + caption` 轉成座標（Geocoding）。

### 9.3 統計

| 項目 | 數值 |
|---|---|
| 收運點 | 20,090 筆，涵蓋 29 個行政區、622 個里 |
| 清運方式 | 沿街 19,114 筆（95.1%）、定點 957 筆（4.8%）、往廠 19 筆 |
| 車牌 | 374 個，每個車牌負責的收運點中位數 38 個、最多 232 個 |
| 每週收運天數 | 5 天 17,703 筆（88.1%）；完全沒有一般垃圾時段 50 筆 |
| 時間格式 | 幾乎全部為 `HH:MM`，1 筆格式異常 |
| 時段長度 | 一般垃圾的收運時段中，95% 開始與結束時間不同，5% 相同（只有單一時間點） |

- **每週哪幾天收：** 若 `d1`～`d7` 依序為星期一至日，週三只有 41 筆、週日 0 筆有一般垃圾時段，其餘每天約 18,600–18,900 筆。
- **一天中的時段：** 一般垃圾開始時間集中在兩段，上午 7–10 時與下午至傍晚 14–19 時。

### 9.4 與動態資料的車牌對應
